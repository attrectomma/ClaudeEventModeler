Why you must learn Event Modeling
Event Modeling addresses one of the most persistent challenges
in the IT industry: communication.
How does it achieve this? At first glance, it might seem like
nothing more than a collection of sticky notes on a board,
connected by arrows. Technically, that’s true—but these sticky
notes create a shared language. And that is precisely what has
been missing for so long.
One of the greatest unresolved challenges has been establishing
a common language that everyone involved in a project can
understand. Event Modeling provides just that—a universal
language that describes requirements so clearly and precisely
that both business stakeholders and developers can fully grasp
what needs to be built.
No special skills are needed to understand, within moments,
how the functionality of a simple to-do app is structured.

WHY YOU MUST LEARN EVENT MODELING
Event Modeling enables software to be visualized step by step,
breaking it down into small, manageable tasks that can be
tackled one at a time. This process creates the “story” of the

What’s truly remarkable about Event Modeling is how it stays

WHAT IS THE “INFORMATION COMPLETENESS CHECK”?
Event Modeling provides a clear and concise language consisting
of only four patterns to describe the individual steps in a soft-
ware system in an easy-to-understand manner. In addition, it
automatically provides a crucial tool for verifying and validating
assumptions: the Information Completeness Check.
Information Completeness Check
The Command doesn’t supply all fields for the Event.
Read models are based on data already stored in the system in
the form of events. This ensures that we never assume data
is available without actually checking if it is. A major reason
software projects get delayed is due to incorrect assumptions
about data. We assume data is available, only to discover during
the implementation phase that it’s not. It’s too easy to make
assumptions.
The Information Completeness Check forces us to look at each
attribute in a Read Model and verify that the data for each
attribute is provided by an Event.
This check doesn’t just apply to Read Models and state views;
it applies to all elements in general. For every attribute in an
Element, you should always verify that the data is provided by
the connected sources. This prevents us from making (wrong)
assumptions, that become more expensive the later we uncover
them.

CAN ONE COMMAND CHANGE MULTIPLE AGGREGATES?
The answer is—of course, it can. But that doesn’t mean it’s a
good idea. If you frequently encounter use cases that require
interacting with multiple aggregates, it might indicate that your
aggregate boundaries are incorrectly defined.
What is an Aggregate?
An aggregate is a consistency boundary. It ensures consistency
within a specific and limited scope of responsibility.
If a single command touches multiple aggregates or swimlanes,
it suggests there are two effects in the system that need to
occur atomically. If that’s the case, these aren’t two separate
aggregates—they’re one.
What I often observe in such scenarios is a thought process like
this:
“When I book my hotel, I also need to book the car.”
That’s certainly true, but does it really need to be consistent at
all times?
Is it acceptable to book the hotel first and then book the car?
And if the car isn’t available, cancel the hotel booking?
Most processes don’t need to be consistent immediately—they
just need to be consistent eventually.

Same principle applies to the infamous bank account example.
There is no atomic operation that deposits money in one account
and withdraws it in another. It´s two eventually consistent
operations.

Can a Command create multiple Events?
The answer is simple—of course.
But it should be the exception, not the rule.
In most cases, there’s a direct correlation between a command
and an event: an action and its result. However, there are
situations where a single command can generate multiple
events, and that’s entirely valid.
Let’s consider a concrete example. Imagine we’re managing a
customer database where each customer can have one or more
addresses. When a new customer is created, we might record
two events: one capturing the fact that the customer was created
(Customer Created) and another reflecting that their initial
address was assigned (Address Assigned).
37

===== page 44 =====
THE LITTLE EVENTMODELING BOOK
Often, instead of having a single action result in multiple events,
you can break it down into several steps using one or more
automations triggered by the initial event.
One important rule I personally follow: a single command
should never interact with multiple swimlanes or aggregates.
The moment you do this, you introduce the need for a transac-
tional boundary around the operation, which adds unnecessary
complexity. (We discussed this in one of the previous chapters
as well.)

Fine-grained Read Models can sometimes be an attempt to

If the requirements specify that a user can only add items with a
valid price to their cart session, you obviously can’t rely on the
client to submit the correct price. The submitted price might be
outdated—or, in the worst case, an attempt at fraud.
When the Command itself acts as the API, there’s no reliable
way to handle this validation unless the business logic operates
directly on the data provided in the Command.
In my view, the Command should include only the data neces-
sary for the business logic to function correctly. In this case,
that means it should contain the accurate, current price.
But where do you get the current prices from?
I recommend retrieving the latest prices from a trusted source
in a layer above the Command Handler. For instance, a Price
